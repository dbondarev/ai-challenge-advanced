# День 7. QLoRA на своём датасете (rerun)

Первый прогон (69% на старом gold) лежит в [`comparison-run1.md`](comparison-run1.md). Ниже — прогон после правки данных из [`data/RERUN.md`](data/RERUN.md).

Тезис: на согласованном gold 1.5B с коротким system даёт **46%** на eval / **16%** на eval2. QLoRA на `train.jsonl` (sql x3, лучший чекпойнт по valid) — **79%** и **65%**. Класс `meeting_held` в train по-прежнему 0: не считаем провалом тюна.

Счёт по классам и kind: [`eval/scores-rerun.md`](eval/scores-rerun.md). Адаптер: [`adapter/`](adapter/) (best valid 0.659, эпоха 5). Параметры: [`params-gold.md`](params-gold.md). Valid по эпохам: [`valid-acc-gold.csv`](valid-acc-gold.csv).

## Что изменилось в данных

Одна договорённость метки (изменение от последнего IN), разные подставные имена, второй тест `eval2.jsonl` (149, 7 проектов не из train). Baseline пересчитан: gold в eval другой.

|---|---|---|

Слабое место — `positive` 14/39 и `sql` 0/2. `no_change` 62/74. Промпт на eval2 почти не работает (16%): без тюна 1.5B не держит правило «изменение vs накопленный статус» на чужих проектах.

## Сравнение с run1

Run1: 50% → 69% на старом eval. Rerun: 46% → **79%** на том же размере, плюс 65% на eval2. Прирост не только от sql x3 и выбора чекпойнта — часть старых 21 ошибок была шумом метки.

`sql` после 3× всё ещё почти не взлетает (0/1 и 0/2). Мало разнообразных шаблонов, не только счётчик строк.

## Что показать

1. `valid-acc-gold.csv`: valid растёт до эпохи 4–5, last = best.
2. Таблица eval 0 / 46 / 79.
3. eval2: промпт 16%, тюн 65% — зачем тюн на этой задаче.
4. `meeting_held`: 0 в train, не ставим в минус модели.
